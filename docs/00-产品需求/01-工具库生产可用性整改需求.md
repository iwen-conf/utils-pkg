# 工具库生产可用性整改需求

## 需求来源

用户认可 2026-08-15 对 `utils-pkg` 能力与实用性的评估，并要求创建足够详细的整改任务文档，交由低质量、低上下文执行模型逐项实施。

## 背景

`utils-pkg` 是一个 Go 1.24 通用工具模块，当前标签为 `v0.3.0`，包含 JWT、密码学、验证码、签名 URL、分页、错误模型、切片、指针和 User-Agent 等能力。项目具备单元测试基础，当前 `go test ./...`、`go test -race ./...`、`go vet ./...` 和模块校验均通过，但存在安全语义、错误链、并发契约、文档真实性和发布治理问题。

当前通过测试不等于满足本需求。现有测试中有一部分固化了错误行为，整改时必须先按目标行为修改测试，再修改实现，不能为了保留绿灯继续兼容不安全行为。

## 目标

1. 修复 JWT、URL 签名、验证码、HMAC 游标和密码学参数处理中的生产风险。
2. 让缓存、错误链、构造器和后台生命周期遵守“失败可见、错误不静默、性能优化不改变正确性”的原则。
3. 收敛重复或误导性的通用能力，明确哪些 API 是生产能力、哪些只是辅助工具。
4. 建立 CI、覆盖率、依赖检查、变更记录和版本一致性门禁。
5. 让 README、包文档、测试与实现成为同一事实来源，不再保留已知失真的能力宣称。
6. 将每项改动拆成单一、可验证、可独立回滚的子任务，便于弱执行模型一次只处理一个目标。

## 使用者与价值

1. 库维护者：需要稳定的 API 边界、清晰的发布规则和可回归测试。
2. 下游 Go 服务开发者：需要不会绕过过期、不会静默降级、不会因无效配置 panic 的工具能力。
3. 间接终端用户：其登录态、密码、验证码、签名链接和错误信息不应因工具库缺陷而失去完整性或泄漏。

## 本轮范围

1. `jwt/`：验证缓存、claims 不可变性、严格解析、刷新令牌重放、吊销错误传播、配置并发和生命周期。
2. `url/`、`pagination/`、`captcha/`：签名绑定、密钥强度、空值验证、错误链和 Unicode 字符集。
3. `crypto/`：AES API 契约、Argon2/scrypt 资源上限、密码策略并发安全和随机数参数校验。
4. `errors/`：标准 `errors.Is/As` 语义、根因保留、JSON 信息泄漏、旧 API 测试和弃用路线。
5. `slice/`、`useragent/`、根包：删除失效能力宣称、修复缓存边界、收敛依赖、修正版本元数据。
6. 工程治理：CI、覆盖率门禁、依赖检查、CHANGELOG、README、项目约束和许可证决策。

## 不做范围

1. 不新增数据库、Redis、消息队列、对象存储或远程服务。
2. 不在本机安装或运行 PostgreSQL、Docker Engine 或长期容器。
3. 不实现完整验证码业务服务；验证码 TTL、发送、存储、尝试次数和风控属于下游业务。
4. 不把 User-Agent 识别升级成设备指纹、反作弊或安全鉴权系统。
5. 不增加 RSA/ECDSA/JWE、多密钥轮换或完整身份平台；JWT 本轮只加固现有 HMAC/HS256 能力。
6. 不发布 tag、不推送远端、不创建 GitHub Release，除非用户另行明确授权。
7. 不为兼容旧行为保留自动回退到不安全签名、弱密钥或宽松校验的路径。
8. 不顺手重写整个仓库；每个子任务只能改其明确列出的路径和调用点。

## 兼容性要求

1. 安全修复优先于对不安全行为的兼容。
2. 必要的公开 API 破坏性变更统一进入下一次次版本 `v0.4.0`，并写入 CHANGELOG 与迁移说明。
3. 能通过新增 API 和明确弃用完成的，不直接删除旧 API；但旧 API 不得继续成为默认安全路径。
4. 禁止用“旧签名验证失败后自动尝试 legacy 算法”等兼容兜底掩盖问题。

## 验收标准

1. 每个已确认 Finding 都有独立子任务、回归测试和失败反例。
2. `go test -count=1 ./...`、`go test -race -count=1 ./...`、`go vet ./...`、`go mod verify` 全部通过。
3. 安全关键包新增针对已知缺陷的回归测试，不允许只提高行覆盖率。
4. 总覆盖率达到任务文档定义的门槛，且 `errors`、`slice` 不再以低覆盖率宣称“完整测试”。
5. README、各包使用说明、版本号和实际 API 一致。
6. 弱执行模型不能自行决定许可证、发布或范围扩张；遇到未决项必须标记阻塞并停止。
