# 项目定位与口径

## 项目定位

1. 产品形态：可被多个 Go 服务导入的基础工具模块，不是独立运行的网络服务。
2. 直接用户角色：库维护者、下游服务开发者、测试/发布人员。
3. 间接安全角色：匿名客户端、已登录用户、持有 refresh token 的用户，以及使用下游服务的管理员或普通用户。
4. 核心价值与关键数据：JWT/会话、密码与哈希、对称密钥、签名 URL/游标、验证码、错误上下文和业务 claims。
5. 信任边界：外部输入进入 token/URL/captcha/KDF 解析；调用方可持有并修改返回对象；外部 `RevocationStore`/刷新消费存储跨进程；错误对象可能进入日志或 HTTP JSON。
6. 本次工作位置：`v0.3.0` 后的生产可用性整改，目标版本含破坏性安全修复时按 `v0.4.0` 管理。

## 项目口径

1. 技术栈：Go module，`go.mod` 声明 Go 1.24；评估环境为 Go 1.26.5 / macOS arm64。
2. 部署形态：库本身无部署；JWT 下游可能单实例或多实例，任务必须分别写清默认内存能力和共享存储能力。
3. 数据与环境：无本地数据库、缓存服务或容器需求；严禁为本任务安装/运行本机 PostgreSQL 或 Docker Engine。
4. 架构限制：只修改当前子任务列出的包；禁止顺手迁移全部 API、引入 Web 框架或增加远程基础设施。
5. Go 错误规则：包装保留 `%w`；判断哨兵错误统一使用标准库 `errors.Is`，类型提取使用 `errors.As`；禁止直接 `err == ErrXxx`/`err != ErrXxx`。
6. 失败策略：构造器和外部存储失败必须返回错误；禁止 stdout 警告、默认关闭日志后静默吞错、返回弱对象同时返回 warning error。
7. 安全测试边界：允许本地单元、竞态、fuzz seed、静态检查和临时测试；禁止未授权远程主动测试。
8. 密钥与证据：文档不得出现真实密钥、完整 token 或下游敏感数据；测试只使用固定假值或随机生成值。
9. 兼容策略：安全问题允许在 `v0.4.0` 做明确破坏性变更；禁止默认 legacy fallback。迁移说明必须同步。
10. 发布权限：任务执行者不得自行 tag、push、发布 Release 或选择许可证。

## 功能角色

| Role | 本次负责人 | 责任 | 禁止事项 |
| --- | --- | --- | --- |
| R-recon | 当前 Codex 审计会话 | 资产、代码证据、Finding、验证基线 | 不改生产代码 |
| R-scan | 未执行；需要时由后续强模型承担 | govulncheck/SAST/SCA 与重排 | 不以扫描替代业务逻辑验证 |
| R-task | 当前 Codex 任务作者 | 前置约束、细粒度子任务、进度表 | 不实施生产修复 |
| R-fix | 后续弱执行模型，每次一个子任务 | 严格按子任务改代码和测试 | 不扩范围、不自行改设计 |
| R-verify | 人类或强模型 | 独立复核行为、测试和 diff | 无证据不得标 `[x]` |

## 已验证基线

1. `go test -count=1 ./...`：通过。
2. `go test -race -count=1 ./...`：通过现有测试路径。
3. `go vet ./...`：通过。
4. `go mod verify`、`go mod tidy -diff`：通过。
5. 总语句覆盖率 66.6%；`errors` 17.8%、`slice` 44.9%、`useragent` 63.2%。
6. Git 工作区在审计开始和结束时均为 `main...origin/main`，无生产代码改动。
