## 目标

## 当前行为

1. legacy Error/Builder/Validator 仍是导出 API，但没有标准 Deprecated 标记。
2. errors README 主要介绍 RichError，根 README 却继续展示 legacy API，推荐路线分裂。
3. 不存在逐项迁移文档，旧伪 Is 的 string 用法也没有 breaking-change 指引。

## 固定推荐路线

1. 业务错误：`NewRich` / 便捷 Rich 构造函数。
2. 包装底层 cause：`WrapRich` 并保留标准 Unwrap。
3. 判断 cause/type：标准库 `errors.Is/As`，当前包导出 Is/As 仅为等价转发。
4. 判断 legacy string code：`IsCode`。
5. 外部响应：`GetStatus()` 或默认 RichError JSON，仅 code/msg。
6. 内部日志：`%+v`、`Cause()`、`Stack()`；禁止把这些值放入响应。

## 必须弃用的入口

至少给以下导出标识添加以 `Deprecated:` 开头的 Go doc；相同家族可在类型/核心 constructor 注释集中说明，但 `go doc` 必须能让调用方看到：

1. `Error`、`New`、`NewWithDetails`、`Wrap`、`WrapWithDetails`。
2. `ErrorType` 及 `FromType/WrapWithType`。
3. `Builder`、`NewBuilder`。
4. `ValidationError`、`Validator`、`NewValidator` 和 convenience validation functions。
5. 旧 utility 中被 Rich/标准库替代的 helper；`Is/As/IsCode` 不弃用。

弃用文本统一说明：“保留至未来明确的 major-version migration；新代码使用 RichError/标准 errors 链。迁移见 MIGRATION.md。”

## MIGRATION 必须包含

1. v0.4.0 的破坏性语义：`Is` 不再接收 string/ErrorType；改用 `IsCode`。
2. legacy → Rich 对照表：构造、包装、code、context、severity/category、validation。
3. `%w` 包装示例和 `errors.Is/As` 示例。
4. JSON 安全边界：旧 Error 公开字段很多，不建议直接作为响应；RichError 默认只 code/msg。
5. 分阶段迁移：新代码先禁止引入 legacy；已有调用点按模块替换；最后 major version 才评估删除。
6. 未覆盖能力：RichError 没有一对一内置 Validator 替代，调用方应保留业务验证库/结构并在边界转换，不要伪造映射。

## 正向验收

1. `go doc ./errors Error`、Builder、Validator 显示 Deprecated。
2. `go doc ./errors RichError` 和 README 推荐路线一致。
3. MIGRATION 每个主要旧入口都有替换或“无一对一替代”说明。
4. example tests 编译并验证标准错误链。

## 反向验收

1. 文档不声称旧 API 已删除。
2. 文档不要求 cold turkey 全仓替换，也不承诺具体删除版本。
3. 不再出现 `errors.Is(err, "CODE")` 或把 ErrorType 传入 Is 的示例。
4. 响应示例不包含 cause/stack/original/context。
