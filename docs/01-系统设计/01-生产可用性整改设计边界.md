# 生产可用性整改设计边界

## 设计目标

本设计固定整改后的目标行为。执行模型不得在子任务中重新选择算法、兼容策略或错误语义；若实现发现本设计与仓库新状态冲突，必须停止并更新任务状态为 `[!]`。

## 总体原则

1. 正确性和安全性优先于缓存、对象池、宽松兼容或“继续可用”。
2. 构造失败返回错误；禁止“返回可用对象，同时返回警告错误”。
3. 标准 Go 错误链是唯一底层语义：包装使用 `%w`，判断使用标准库 `errors.Is/As`。
4. 对外输入中的计算参数必须有显式上下限，避免攻击者控制 CPU、内存或分配规模。
5. 缓存只能保存验证结果，不能延长 token、签名或业务对象本身的有效期。
6. 对外返回与日志诊断分离；响应序列化不得自动包含底层 cause、密钥或完整 token。
7. 公共可变配置若宣称并发安全，必须不可变或在全部读写路径上同步；不能只给部分字段加锁。

## JWT 目标设计

### 校验策略

1. 只接受 `HS256`，使用 `jwt.WithValidMethods([]string{jwt.SigningMethodHS256.Alg()})`，禁止仅判断“HMAC 家族”。
2. 所有本库生成和验证的 token 必须包含合法 `exp`，解析使用 `jwt.WithExpirationRequired()`。
3. `StandardClaims.UnmarshalJSON` 必须检查 `GetSubject`、`GetIssuer`、`GetAudience`、`GetIssuedAt`、`GetExpirationTime`、`GetNotBefore` 的错误；任何类型错误都返回带字段名且保留根因的错误。
4. `JWTOptions.Issuer`、`Audience` 继续作为签发默认值；新增独立的 `ExpectedIssuer`、`ExpectedAudience` 作为验证约束。期望值为空时不强制该字段，非空时分别使用 `jwt.WithIssuer`、`jwt.WithAudience` 或 `jwt.WithAllAudiences`。
5. 密钥规则只验证至少 32 字节，不再用字符类别猜测熵；允许高熵十六进制和机器生成密钥，文档要求密钥来自 CSPRNG/密钥管理系统。

### 缓存策略

1. `cacheItem` 保存独立克隆的 claims 和绝对 `validUntil`。
2. 成功结果的 `validUntil` 为 `min(cache写入时间+CacheTTL, claims.ExpiresAt)`；负缓存只使用 `CacheTTL`。
3. 命中缓存时先检查 `validUntil`，过期立即删除并重新走完整解析；不得只检查缓存写入时间。
4. 写入缓存时克隆，返回调用方时再次克隆。`Audience`、`NumericDate` 指针和 `CustomClaims` 中 JSON 兼容的嵌套 map/slice 都要独立复制。
5. 任何调用方对返回 claims 的修改都不能影响缓存或其他请求。

### Refresh 重放与吊销

1. 新增独立的刷新令牌消费存储接口，不把一次性消费语义硬塞入现有 `RevocationStore`。
2. 接口至少提供原子 `Consume(ctx, jti, expiresAt) (firstUse bool, err error)` 和只读 `IsConsumed(ctx, jti) (bool, error)`；默认实现为进程内存，外部实现必须可用 Redis SETNX、唯一键或事务实现跨实例原子性。
3. 存储错误必须失败关闭并返回错误，不能继续签发新 token。
4. 多实例安全文档必须明确：只有注入共享、原子消费存储后才具备跨实例 refresh 防重放能力。

### 生命周期与配置

1. `Shutdown` 使用 `sync.Once`，重复或并发调用不 panic。
2. 动态配置保留时，增加统一配置锁并在读路径取快照；若某字段无法安全动态修改，则删除 setter 并只允许构造时配置。
3. `IsBlacklisted`、`CleanBlacklist`、`GetBlacklistSize` 不得吞掉存储错误。优先增加返回 `error` 的明确 API，再将旧无错误 API 标记弃用且不作为内部默认路径。

## URL 签名目标设计

1. 新签名格式使用显式版本 `_sigv=2`；默认验证只接受 v2，不自动回退旧算法。
2. 规范串固定为：版本、HTTP 方法、scheme、host（含端口）、escaped path、去掉 `_sign` 后的 canonical query，各字段用换行分隔。
3. `URLBuilder` 默认方法为 `GET`，增加 `SetMethod`；`Build` 与 `ValidateSignature` 继续以 GET 为默认，并新增按方法验证的 API。
4. scheme 和 host 统一小写；path 为空按 `/`；fragment 不参与签名并在文档中声明其不属于服务器请求。
5. 仅允许绝对 `http`/`https` URL，拒绝空 host、userinfo、opaque URL。
6. HMAC 密钥至少 32 字节；签名使用 `base64.RawURLEncoding`。
7. `_exp` 必须存在且为正数；时间戳未来漂移仍受限。调用方给出的 `maxAgeSeconds` 只能进一步缩短有效期，不能放宽签名中 `_exp`。

## Pagination 与 Captcha 目标设计

1. `NewHMACCodec` 对空或不足 32 字节密钥返回 `nil, error`，不得返回仍可工作的 codec。
2. HMAC codec 复制输入密钥；零值、nil receiver 或未初始化内部 codec 的 `Encode/Decode` 返回明确错误，不以空密钥签名。
3. Captcha `Validate` 在 trim 后任一值为空时返回 false；长度不同时返回 false；等长时使用 `subtle.ConstantTimeCompare`。
4. Captcha 只负责生成与比较，不新增 TTL、存储、限流和尝试次数状态。
5. 自定义字符集按 `[]rune` 处理，输出长度按 rune 数；重复 rune 去重，少于 2 个唯一字符返回错误。

## Crypto 目标设计

1. AES 只支持 GCM。保留 `NewAESEncryptorWithMode` 时，`ModeCFB` 和未知模式返回错误；禁止打印 stdout 警告或静默改用 GCM。
2. 删除未使用的 key 字段、无意义锁和未实际参与加密的 bufferPool；不保留“看起来像优化”的死代码。
3. Argon2 上限：memory 8 MiB–256 MiB（参数单位为 KiB）、iterations 1–10、parallelism 1–16、salt 16–64 字节、key 16–64 字节、编码字符串不超过 4096 字节。
4. scrypt 要求 N 为大于 1 的 2 次幂，估算内存 `128*N*r` 不超过 256 MiB，r 为 1–32，p 为 1–16，salt/key 均为 16–64 字节，编码字符串不超过 4096 字节；所有乘法先做溢出检查。
5. Hash 和 Verify 在调用 KDF 前使用同一验证函数；解析后的参数必须先验证再计算。
6. `PasswordPolicy` 不再暴露可被并发直接修改的字段；使用配置值对象、克隆输入 slice、原子替换编译结果；长度使用 rune 数。

## Errors 目标设计

1. 包内导入标准库错误包时使用 `stderrors` 别名，避免与当前包名混淆。
2. `Is(err, target error)`、`As(err error, target any)` 直接委托标准库；代码匹配使用新的 `IsCode`，不再把 string 塞给伪 `Is`。
3. `GetCode`、`GetSeverity`、`GetCategory`、`FromRichError` 等通过标准 `errors.As` 穿透 `%w` 链。
4. `RichError.MarshalJSON` 默认只输出 `code` 和 `msg`；cause 和 stack 只能通过显式日志接口或 `%+v` 输出。
5. 旧 `Error`/Builder/Validator 本轮不立即删除，但标记弃用、补足测试和迁移说明；新文档默认推荐 `RichError` + 标准错误链。
6. `In/NotIn` 不能对不可比较值使用 `==`；长度和空值判断覆盖全部整数/浮点类型和 Unicode。

## 通用工具与发布目标设计

1. 删除 `slice` 中没有调用者的私有 parallel 函数和对应“自动并行”文档；不把不确定顺序的并行 Filter 作为默认能力。
2. 使用标准库 `cmp.Ordered`，移除仅为 constraints 引入的 `golang.org/x/exp` 直接依赖。
3. 删除未使用且无测试的 `slice.LRUCache`，在 `v0.4.0` 迁移说明中记录；User-Agent 内部缓存用 `container/list + map` 实现 O(1) LRU，并对无效容量失败。
4. User-Agent 结果只用于统计和展示，不用于权限、风控或机器人封禁。
5. tag 是版本事实来源；硬编码 `Version()` 必须与目标发布一致并由测试约束。涉及破坏性变更的下一版本为 `v0.4.0`。
6. 发布前必须有 CI、覆盖率门禁、CHANGELOG、迁移说明和许可证决策；未经用户授权不创建 tag 或推送。
